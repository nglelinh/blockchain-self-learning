# Bài giảng: Sharding — Xử lý song song trên Blockchain

Hãy hình dung một siêu thị khổng lồ có 10.000 nhân viên thu ngân, nhưng quy định bắt buộc **cả 10.000 người phải cùng nhau bấm máy tính lại từng hóa đơn mua một ly cà phê** trước khi khách được ra về! Đó chính xác là nút thắt cổ chai của các blockchain cổ điển: càng thêm nhiều nút mạng, bảo mật càng cao nhưng tốc độ xử lý lại chẳng hề tăng lên.

**Sharding (phân mảnh)** giải quyết nghịch lý đó bằng ý tưởng chia xa lộ 1 làn thành $$k$$ làn chạy song song: mỗi nhóm validator chỉ kiểm chứng một phân mảnh giao dịch riêng. Nhưng chia nhỏ lực lượng lập tức đặt ra một câu đố xác suất sống còn: *nếu kẻ tấn công chỉ nắm 30% tổng số validator toàn mạng, làm sao ngăn chúng tập trung toàn bộ lực lượng vào chiếm đoạt đúng 1 phân mảnh nhỏ?*

---

## Bản đồ kiến thức nền: Sharding trong hệ phân tán và xác suất ủy ban là gì?

Để hiểu sâu Sharding ở trình độ đại học, ta cần ghép nối **ba trụ cột toán học và hệ thống**:

1. **Phân mảnh trạng thái & thực thi (State/Execution Sharding):** Chia toàn bộ sổ cái và không gian địa chỉ thành $$k$$ phân mảnh độc lập để tổng thông lượng tăng tuyến tính theo $$k$$, kèm giao thức khóa nguyên tử (cross-shard receipts) cho giao dịch xuyên phân mảnh.
2. **Xác suất chọn ủy ban ngẫu nhiên (Random Sampling & Binomial Tail):** Dùng nguồn ngẫu nhiên không thể thao túng (RANDAO / VDF) để bốc thăm validator vào từng phân mảnh; bảo mật được định lượng trực tiếp qua đuôi phân phối Nhị thức / Siêu bội.
3. **Khả dụng dữ liệu (Data Availability Sampling — DAS):** Xu hướng hiện đại (Danksharding) thay vì phân mảnh thực thi phức tạp, chỉ phân mảnh *dữ liệu* nhờ **mã hóa xóa Reed–Solomon 2D** để nút nhẹ chỉ cần lấy mẫu ngẫu nhiên vài chục mảnh nhỏ là chắc chắn 99.9999% dữ liệu đã được công bố đầy đủ.

## 1. Tổng quan về khái niệm

**Sharding (Phân mảnh)** là kỹ thuật chia mạng blockchain thành nhiều chuỗi song song (shard), trong đó mỗi shard xử lý một tập con các giao dịch. Mục tiêu của hướng tiếp cận này là mở rộng thông lượng theo tỷ lệ tuyến tính với số lượng shard (chẳng hạn 64 shard cho tổng thông lượng gấp 64 lần một chuỗi đơn lẻ).

**Nguồn gốc từ cơ sở dữ liệu**:

Sharding không phải khái niệm mới mà đã được ứng dụng rộng rãi trong hệ quản trị cơ sở dữ liệu truyền thống:

```
Traditional Database:
- Single server: 10,000 queries/second
- Problem: Cannot handle more load

Sharded Database:
- Split data across 10 servers
- Each handles different data subset
- Total: 100,000 queries/second
- 10× improvement!
```

**Thách thức của Sharding trên Blockchain**:

Phân mảnh cơ sở dữ liệu truyền thống đơn giản hơn vì có bộ điều phối tập trung, trong khi phân mảnh blockchain phức tạp hơn nhiều do yêu cầu phi tập trung:

```
Database Sharding:
✓ Central coordinator assigns data
✓ Trust database admin
✓ Can communicate between shards easily

Blockchain Sharding:
✗ Must maintain decentralization
✗ Must handle cross-shard transactions
✗ Must prevent single-shard attacks
✗ Must ensure data availability
✗ More complex consensus
```

**Tầm nhìn Sharding trên Ethereum**:

```
Current Ethereum:
- 1 chain
- All validators process ALL transactions
- Throughput: ~15 TPS
- Bottleneck: Every node does everything

Sharded Ethereum:
- 64 shards + 1 beacon chain
- Validators assigned to specific shards
- Each shard: ~15 TPS
- Total: 64 × 15 = 960 TPS base
- With rollups: 960 × 100 = 96,000 TPS!

64× on-chain improvement!
10,000× với rollups!
```

**Quá trình điều chỉnh lộ trình Sharding của Ethereum**:

- **Giai đoạn 1 (2017–2020 — Thiết kế ban đầu)**: 1.024 shard với phân mảnh toàn bộ tầng thực thi; độ phức tạp kỹ thuật quá cao.
- **Giai đoạn 2 (2020–2022 — Đơn giản hóa)**: 64 shard dữ liệu, chuyển tầng thực thi lên rollup theo lộ trình lấy rollup làm trung tâm (rollup-centric roadmap).
- **Giai đoạn 3 (2022–2024 — Danksharding)**: Thiết kế hợp nhất thị trường phí và phân mảnh dữ liệu, bắt đầu từ Proto-Danksharding (EIP-4844) rồi tiến tới Danksharding đầy đủ để cung cấp khả dụng dữ liệu cho rollup.

## 2. Hiểu biết trực quan

### 2.1. Sharding như nhiều quầy thu ngân song song

**Một làn xử lý** (Blockchain truyền thống):
```
Supermarket:
- 1 checkout lane
- 1000 customers
- Each takes 1 minute
- Total time: 1000 minutes (~17 hours!)

Everyone waits in same line
Slow but fair
```

**Nhiều làn xử lý song song** (Sharding):
```
Supermarket:
- 10 checkout lanes (shards)
- 1000 customers
- Distributed across lanes
- Total time: 100 minutes (~1.7 hours!)

10× faster!
But: Must ensure fair distribution
```

**Thách thức**: Giao dịch xuyên shard (Cross-shard transactions)
```
Customer 1 in Lane A wants to split payment with Customer 2 in Lane B
→ Lanes must coordinate!
→ Adds complexity
```

### 2.2. Beacon Chain đóng vai trò "Đài kiểm soát không lưu"

**Kiến trúc Sharding của Ethereum**:

```
        Beacon Chain (Coordinator)
              /    |    \
             /     |     \
            /      |      \
      Shard 0  Shard 1 ... Shard 63
      
Beacon Chain:
- Coordinates validators
- Assigns validators to shards
- Maintains finality
- Handles cross-shard messages

Shards:
- Process transactions independently
- Report to Beacon Chain
- Receive cross-shard messages
```

**Liên hệ trực quan**:
```
Air Traffic Control = Beacon Chain
- Coordinates all planes (shards)
- Ensures no collisions
- Manages communication

Individual planes = Shards  
- Fly independently
- Report to control
- Follow coordination
```

### 2.3. Lấy mẫu khả dụng dữ liệu (Data Availability Sampling — DAS)

**Vấn đề**:

```
Sharded data:
- Too much for single node to download
- Need to verify data available
- Without downloading everything

Like: Library với millions of books
     Want to verify all books exist
     Without reading every book!
```

**Giải pháp — Lấy mẫu ngẫu nhiên kết hợp mã xóa (Erasure Coding)**:

```
Data Availability Sampling (DAS):

1. Data split into chunks (and extended with erasure coding)
2. Node randomly samples k chunks
3. If all samples valid and available:
   → High probability ALL data available
4. Repeat sampling multiple times

Math:
- Without erasure coding, 1% missing data with 30 samples → ~26% chance detect
- With erasure coding (attacker must withhold >50% to block recovery):
  Sampling 30 chunks → >99.9999% chance detect missing data!

Efficient verification!
```

### 2.4. Giao tiếp xuyên shard (Cross-Shard Communication)

**Thách thức**:

```
Alice (Shard 0): Has 100 tokens
Bob (Shard 1): Address receiving tokens

Transaction: Alice → Bob (100 tokens)

Problem:
- Alice's balance on Shard 0
- Bob's balance on Shard 1
- How to coordinate?
```

**Hai hướng giải quyết chính**:

**Hướng 1: Biên lai (Receipts)**
```
1. Shard 0: Deduct 100 from Alice
2. Shard 0: Create receipt: "100 tokens for Shard 1"
3. Receipt posted to Beacon Chain
4. Shard 1: Reads receipt
5. Shard 1: Credit 100 to Bob

Atomic: Either both happen or neither
```

**Hướng 2: Khóa tài sản (Locking)**
```
1. Lock Alice's 100 tokens on Shard 0
2. Create proof of lock
3. Shard 1 verifies proof
4. Credit Bob on Shard 1
5. Burn locked tokens on Shard 0

Two-phase commit across shards
```

### 2.5. Phân bổ validator ngẫu nhiên

Việc phân bổ ngẫu nhiên là điều kiện thiết yếu để đảm bảo an ninh cho từng shard:

```
Security threat: If attacker controls validator assignment
└─ Could assign all malicious validators to one shard
└─ Take over that shard!

Solution: Random unpredictable assignment
└─ Validator rotation every epoch
└─ Reshuffling prevents coordination
└─ Based on RANDAO (VDF)

Result: Attacker must control >1/3 of TOTAL stake
       (not just shard stake)
```

### 3.1. Kiến trúc Sharding

**Beacon Chain (Tầng điều phối)**:

```python
class BeaconChain:
    """Ethereum Beacon Chain managing shards"""
    
    def __init__(self, num_shards=64):
        self.num_shards = num_shards
        self.shards = [Shard(i) for i in range(num_shards)]
        self.validators = []
        self.current_epoch = 0
    
    def assign_validators_to_shards(self):
        """Randomly assign validators to shards"""
        import random
        
        # Shuffle validators
        shuffled = self.validators.copy()
        random.shuffle(shuffled)
        
        # Distribute across shards
        validators_per_shard = len(self.validators) // self.num_shards
        
        for i, shard in enumerate(self.shards):
            start = i * validators_per_shard
            end = start + validators_per_shard
            shard.validators = shuffled[start:end]
            
            print(f"Shard {i}: {len(shard.validators)} validators assigned")
    
    def process_cross_shard_tx(self, tx):
        """Handle transaction across shards"""
        from_shard = tx['from_shard']
        to_shard = tx['to_shard']
        
        # Phase 1: Deduct from source shard
        receipt = self.shards[from_shard].create_receipt(tx)
        
        # Phase 2: Credit to destination shard
        self.shards[to_shard].process_receipt(receipt)
        
        print(f"Cross-shard TX: Shard {from_shard} → Shard {to_shard}")
```

## 4. Công thức toán học và bảo mật

### 4.1. Mở rộng thông lượng

**Không có Sharding**:

\[
\text{TPS}_{\text{total}} = \text{TPS}_{\text{single chain}}
\]

**Có Sharding**:

\[
\text{TPS}_{\text{total}} = n \times \text{TPS}_{\text{per shard}}
\]

Trong đó \( n \) là số lượng shard.

**Ví dụ**:
```
Single chain: 15 TPS
64 shards: 64 × 15 = 960 TPS

Linear scaling!
```

**Kết hợp Rollups trên các Shard**:

\[
\text{TPS}_{\text{total}} = n_{\text{shards}} \times m_{\text{rollups/shard}} \times \text{TPS}_{\text{rollup}}
\]

```
64 shards × 10 rollups/shard × 100 TPS/rollup
= 64,000 TPS!

Exponential scaling!
```

### 4.2. Phân tích bảo mật — Tấn công một shard đơn lẻ

**Xác suất kiểm soát ít nhất một shard**:

Với \( n \) shard, mỗi shard có \( m \) validator và kẻ tấn công kiểm soát tỷ lệ \( \alpha \) tổng tập validator:

\[
P(\text{corrupt ≥1 shard}) = 1 - \left(1 - P(\text{corrupt single shard})\right)^n
\]

**Xác suất kiểm soát một shard đơn lẻ**:

Cần kiểm soát ít nhất \( 2/3 \) số validator của shard đó; theo phân phối nhị thức:

\[
P(\text{corrupt shard}) = \sum_{k=\lceil 2m/3 \rceil}^{m} \binom{m}{k} \alpha^k (1-\alpha)^{m-k}
\]

**Ví dụ tính toán**:
```
Total validators: 10,000
Shards: 64
Validators per shard: 10,000 / 64 ≈ 156
Attacker stake: 10%

P(control 2/3 of one shard):
Using normal approximation:
≈ Φ((0.1 - 0.667) / √(0.1×0.9/156))
≈ Φ(-23.5)
≈ 10^-122 (essentially impossible!)

With 64 shards:
P(corrupt ≥1) ≈ 64 × 10^-122 ≈ 10^-120

Still impossible!
```

**Điều kiện kích thước ủy ban trên mỗi shard**:

\[
m \geq \frac{9\log(n)}{\epsilon^2} \quad \text{for security parameter } \epsilon
\]

Khi số lượng shard tăng, mỗi shard cũng cần số validator đủ lớn để giữ xác suất bị tấn công ở mức rất nhỏ.

### 4.3. Độ trễ giao dịch xuyên shard

**Thời gian hoàn tất giao dịch xuyên shard**:

\[
T_{\text{cross-shard}} = T_{\text{shard1}} + T_{\text{beacon}} + T_{\text{shard2}}
\]

**Ví dụ**:
```
Shard 1 processes: 1 slot (12 seconds)
Beacon includes receipt: 1 slot (12 seconds)
Shard 2 processes receipt: 1 slot (12 seconds)

Total: 36 seconds (vs 12s for same-shard)

3× slower for cross-shard!
```

**Tối ưu hóa**: Xử lý xuyên shard bất đồng bộ giúp không chặn luồng thực thi cục bộ, tương tự mô hình nhất quán cuối cùng (eventual consistency).

### 4.4. Toán học của lấy mẫu khả dụng dữ liệu (DAS)

**Bài toán**: Xác minh \( N \) mảnh dữ liệu đều khả dụng mà không cần tải toàn bộ.

**Giải pháp**: Lấy mẫu ngẫu nhiên \( k \) mảnh.

**Xác suất phát hiện dữ liệu bị thiếu**:

Nếu tỷ lệ \( p \) số mảnh dữ liệu bị thiếu:

\[
P(\text{detect}) = 1 - (1 - p)^k
\]

**Ví dụ**:
```
Missing data: p = 1% (1% chunks unavailable)
Sample size: k = 30 chunks

P(detect) = 1 - (0.99)^30
          = 1 - 0.74
          = 0.26 = 26%

Not great! Need more samples.

With k = 100:
P(detect) = 1 - (0.99)^100 = 1 - 0.366 = 63.4%

With k = 300:
P(detect) = 1 - (0.99)^300 = 95%

Trade-off: More samples = better detection but higher cost
```

**Mã xóa (Erasure Coding)**:

Mở rộng dữ liệu với hệ số dư thừa \( r \):

\[
\text{Expanded Data} = \text{Original} \times (1 + r)
\]

```
Original: 100 chunks
Redundancy: 50% (r = 0.5)
Expanded: 150 chunks

Property: Can reconstruct original from ANY 100 of 150 chunks

Even if 50 chunks missing → Can recover!
```

### Khung giải thích: tự tay tính xác suất kẻ tấn công chiếm đoạt 1 shard (nên đọc chậm)

Giả sử toàn mạng có hàng chục nghìn validator, trong đó kẻ tấn công kiểm soát tỷ lệ $$p = 30\%$$ (không đủ phá đồng thuận toàn mạng vốn cần $$> 50\%$$ hoặc $$> 33\%$$). Ta bốc thăm ngẫu nhiên $$m$$ validator lập thành ủy ban cho Shard #1, và kẻ tấn công thắng nếu chiếm được quá nửa ủy ban ($$X > m/2$$).

1. **Nếu ủy ban quá nhỏ ($$m = 5$$ validator — cần $$X \ge 3$$ để chiếm shard):**
   Dùng công thức phân phối Nhị thức $$P(X = k) = \binom{m}{k}p^k(1-p)^{m-k}$$:
   - $$P(X = 3) = \binom{5}{3}(0.3)^3(0.7)^2 = 10 \times 0.027 \times 0.49 = 0.1323$$.
   - $$P(X = 4) = \binom{5}{4}(0.3)^4(0.7)^1 = 5 \times 0.0081 \times 0.7 = 0.02835$$.
   - $$P(X = 5) = (0.3)^5 = 0.00243$$.
   - Tổng xác suất mất shard: **$$P(X \ge 3) \approx 16.31\%$$** — cứ 6 lần bốc thăm lại mất shard 1 lần, hoàn toàn bất an!

2. **Khi tăng cỡ ủy ban lên $$m = 128$$ (như chuẩn Ethereum Beacon Chain — cần $$X \ge 65$$):**
   - Kỳ vọng số nút xấu trong ủy ban: $$\mu = mp = 128 \times 0.3 = 38.4$$.
   - Độ lệch chuẩn: $$\sigma = \sqrt{mp(1-p)} = \sqrt{128 \times 0.3 \times 0.7} \approx 5.18$$.
   - Ngưỡng chiếm đoạt $$65$$ nằm cách trung bình tới:
     $$
     z = \frac{65 - 38.4}{5.18} \approx +5.13\,\sigma!
     $$
   Ở khoảng cách hơn $$5.1\sigma$$, xác suất đuôi rơi xuống **dưới $$10^{-7}$$** (chưa tới 1 phần 10 triệu)!

**Bài học thiết kế:** Sharding an toàn không phải phép màu — nó là cuộc đánh đổi trực tiếp giữa **số lượng shard $$k$$** và **kích thước tối thiểu $$m$$ của mỗi ủy ban** để chặn xác suất đuôi Nhị thức dưới mức $$10^{-9}$$.

## 5. Góc nhìn triển khai

### 5.1. Hệ thống Sharding mô phỏng đơn giản

```python
import hashlib
import random
from typing import List, Dict

class ShardedBlockchain:
    """Simplified sharded blockchain system"""
    
    def __init__(self, num_shards=4):
        self.num_shards = num_shards
        self.shards = [Shard(i, num_shards) for i in range(num_shards)]
        self.beacon = BeaconChain(self.shards)
        self.validators = []
    
    def register_validator(self, validator_id, stake):
        """Register validator"""
        validator = {
            'id': validator_id,
            'stake': stake,
            'shard': None
        }
        self.validators.append(validator)
    
    def assign_validators(self):
        """Randomly assign validators to shards"""
        # Shuffle for randomness
        shuffled = self.validators.copy()
        random.shuffle(shuffled)
        
        # Distribute evenly
        for i, validator in enumerate(shuffled):
            shard_id = i % self.num_shards
            validator['shard'] = shard_id
            self.shards[shard_id].add_validator(validator)
        
        print(f"\n✓ Validators assigned to {self.num_shards} shards")
        for shard in self.shards:
            print(f"  Shard {shard.shard_id}: {len(shard.validators)} validators")
    
    def process_transaction(self, from_addr, to_addr, amount):
        """Process transaction (may be cross-shard)"""
        from_shard = self._get_shard_for_address(from_addr)
        to_shard = self._get_shard_for_address(to_addr)
        
        tx = {
            'from': from_addr,
            'to': to_addr,
            'amount': amount,
            'from_shard': from_shard,
            'to_shard': to_shard
        }
        
        if from_shard == to_shard:
            # Same shard - process directly
            self.shards[from_shard].process_local_tx(tx)
            print(f"✓ Local TX on Shard {from_shard}")
        else:
            # Cross-shard - use receipts
            self.beacon.process_cross_shard_tx(tx, self.shards)
            print(f"✓ Cross-shard TX: Shard {from_shard} → Shard {to_shard}")
    
    def _get_shard_for_address(self, address):
        """Determine shard for address (consistent hashing)"""
        addr_hash = int(hashlib.sha256(address.encode()).hexdigest(), 16)
        return addr_hash % self.num_shards
    
    def get_balance(self, address):
        """Get balance (may need to query specific shard)"""

class Shard:
    """Individual shard"""
    
    def __init__(self, shard_id, total_shards):
        self.shard_id = shard_id

        self.state = {}  # address → balance
        self.validators = []
        self.tx_count = 0
    
    def add_validator(self, validator):
        """Add validator to shard"""
        self.validators.append(validator)
    
    def process_local_tx(self, tx):
        """Process transaction within shard"""
        from_addr = tx['from']
        to_addr = tx['to']
        amount = tx['amount']
        
        # Initialize if needed
        if from_addr not in self.state:
            self.state[from_addr] = 0
        if to_addr not in self.state:
            self.state[to_addr] = 0
        
        # Execute
        if self.state[from_addr] >= amount:
            self.state[from_addr] -= amount
            self.state[to_addr] += amount
            self.tx_count += 1
            return True
        
        return False

class BeaconChain:
    """Beacon chain coordinating shards"""
    
    def __init__(self, shards):
        self.shards = shards
        self.cross_shard_queue = []
    
    def process_cross_shard_tx(self, tx, shards):
        """Coordinate cross-shard transaction"""
        from_shard_id = tx['from_shard']
        to_shard_id = tx['to_shard']
        
        # Phase 1: Source shard creates receipt
        receipt = shards[from_shard_id].create_cross_shard_receipt(tx)
        
        if receipt:
            # Phase 2: Queue for destination shard
            self.cross_shard_queue.append(receipt)
            
            # Phase 3: Destination shard processes
            success = shards[to_shard_id].process_cross_shard_receipt(receipt)
            
            if success:
```
